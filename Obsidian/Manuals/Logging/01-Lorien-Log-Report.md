# Daily log report (lorien)

Lorien is the central rsyslog server (`10.66.66.10`), receiving logs from gondor and shire over TCP 514 into `/var/log/remote/`. A daily cron job on lorien scans that store for errors/critical entries across all hosts and emails a summary.

Script: `scripts/bash/lorien_log_report.sh` in this repo, deployed to `/usr/local/bin/lorien_log_report.sh` on lorien.

## How it picks up "yesterday"

`/var/log/remote/*.log` is rotated daily (`dotfiles/system/rsyslog/fedora/logrotate-remote`, `delaycompress`) by a systemd timer around 00:20 Europe/Warsaw. The freshly rotated file is suffixed with the rotation date (today), but its contents are the full previous calendar day, still uncompressed for one cycle. The cron job runs at 06:00 — well after rotation — and reads `*.log-$(date +%Y%m%d)` per host, skipping the `-messages`/`-secure`/`-cron` split files since the base `.log` file is already the facility/level catch-all.

`logrotate-remote` has a `postrotate` hook that sends `SIGHUP` to `rsyslog.service` after rotation. Without it, rsyslogd can keep writing to the renamed (old) file through its cached dynafile descriptor instead of reopening the new one — observed in practice on the `jawor` dynafile, where today's entries kept landing in yesterday's rotated file while the new `jawor.log` stayed empty. The HUP forces rsyslogd to reopen all dynafile handles by path right after rotation, so the "rotated file = clean single-day snapshot" assumption above actually holds.

Hosts are discovered dynamically from whatever `*.log-<date>` files exist that day — no hardcoded host list. lorien's own logs (not routed through `/var/log/remote`) are pulled separately via `journalctl -p err..emerg`.

Matching is keyword-based (`error|err|fail|critical|crit|emerg|panic`, case-insensitive) since the rsyslog file format doesn't print severity as text — this is a heuristic, not a strict priority filter.

## Email format

The email body is a short Polish-language summary generated by the Claude Code CLI (`claude -p --model claude-haiku-4-5-20251001`, given the full raw report on stdin). The model is pinned to Haiku — the cheapest tier — since this is a daily, low-stakes summarization task; the deeper investigation/fix work happens interactively via the `lorien-log-fix` skill instead. The full raw report is attached as a `.txt` file (base64, hand-built `multipart/mixed` MIME message — no `mail`/`mutt` needed, just `msmtp` as the SMTP transport). If the `claude` call fails or times out (60s), the summary falls back to a placeholder string and the attachment is still sent, so a broken AI call never blocks delivery of the underlying data.

## Mail delivery

lorien had no MTA installed. Mail is sent via `msmtp` through Gmail SMTP relay to `bjawornicki@gmail.com`, using a Google App Password (requires 2-Step Verification on the Google account: https://myaccount.google.com/apppasswords).

Config template: `dotfiles/system/rsyslog/fedora/msmtprc.example` → deploy as `/etc/msmtprc` on lorien (mode `600`, `root:root`). **The real file with the actual app password is never committed** — only the `.example` template lives in the repo.

## AI summary (Claude Code CLI)

Node.js + `@anthropic-ai/claude-code` (npm, global install) run on lorien to produce the summary. Auth is a long-lived OAuth token from `claude setup-token`, which requires an interactive browser login — this **cannot be scripted/automated**, it must be run once by hand:

```bash
ssh lorien
claude setup-token   # as root; opens a browser login flow
```

The resulting token is stored in `/etc/claude-cron.env` (mode `600`, `root:root`) as `CLAUDE_CODE_OAUTH_TOKEN=...`, sourced by the report script before calling `claude -p`. This file is never committed — no template exists in the repo since the token is account-specific and long-lived (not a value you'd want to regenerate from a placeholder). If the token ever expires or is revoked, re-run `claude setup-token` and overwrite `/etc/claude-cron.env`.

## Deployment

```bash
scp scripts/bash/lorien_log_report.sh lorien:/usr/local/bin/lorien_log_report.sh
ssh lorien 'chmod 750 /usr/local/bin/lorien_log_report.sh'

# one-time mail setup
ssh lorien 'dnf install -y msmtp'
scp dotfiles/system/rsyslog/fedora/msmtprc.example lorien:/etc/msmtprc
ssh lorien 'chmod 600 /etc/msmtprc'
# then edit /etc/msmtprc on lorien to replace CHANGE_ME_APP_PASSWORD

# one-time Claude CLI setup
ssh lorien 'dnf install -y nodejs && npm install -g @anthropic-ai/claude-code'
ssh lorien  # then interactively: claude setup-token
# then create /etc/claude-cron.env on lorien with CLAUDE_CODE_OAUTH_TOKEN=<token>, chmod 600

# cron (root's crontab on lorien)
ssh lorien 'crontab -l 2>/dev/null | { cat; echo "0 6 * * * /usr/local/bin/lorien_log_report.sh"; } | crontab -'
```

Reports are also kept as files under `/var/log/reports/` on lorien (30-day retention), regardless of whether email delivery succeeds.
